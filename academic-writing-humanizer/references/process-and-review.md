# Process and review: H and I

## Requirements

Check exact programme, document type, cycle and official policy. Record URL/date/permitted uses/disclosure/unknowns. Departments differ; a formal-application policy need not describe an informal email. If drafting is disallowed but feedback is allowed, use critique within the applicable scope. If unclear, explain uncertainty while continuing useful independent work such as source verification. Do not infer new permission requests from generic recommendations.

Describe actual activities in any disclosure: idea generation, structure, prose drafting, method suggestions, retrieval, citation checks, translation and copyediting. Include tool/model only when known. Do not say grammar-only when AI supplied substantial intellectual content or prose.

## Real records

Preserve original input, drafts, changes, sources and actual decisions. Use actual file timestamps; label retrospective summaries. Never fabricate earlier drafts, typing traces, reading notes or backdated evidence.

## Rubric

Use satisfactory / needs revision / unresolved / not applicable, each with evidence. Never aggregate into an AI probability.

| Dimension | Check |
|---|---|
| Background | Supported and modestly framed? |
| Voice | Genuine samples and justified comparison? |
| Question | Focus and defensible contribution? |
| Data/design | Observable measures, justified design, explicit access/limits? |
| Fit | Specific accurate connection, no invented relationship? |
| Sources | Identity/support checked at the stated access level? |
| Language | Clear flow and natural syntax, with every protected proposition intact? Use style-review.md to judge fidelity and readability separately. |
| Process | Actual AI/author roles and decisions recorded? |
| Understanding | Author has answered questions? Otherwise untested. |

For independent review, supply raw requirements/draft/evidence, not desired verdict or editing rationale. For A/B review randomize labels, keep the mapping outside reviewer inputs, and preserve the raw verdict. Writing may reveal revision order, so do not promise perfect blinding. Report failures and corrections.

Generate 5–8 substantive discussion questions. Generated answers do not prove the user's understanding. Separate questions, working notes and unresolved choices from submission prose.

## Detector record

Record product/date/version if known/document hash/eligibility/literal result/report file/interpretation/limits. Without an actual run use `not tested` and `percentage unavailable`. Never convert another tool's output or subjective review into a Turnitin prediction. No acceptance or undetectability guarantee.
